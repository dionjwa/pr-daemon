The one thing to know

The agent label is the only trigger, and it works on an issue or a pull request. Either way the branch gets the same bring-up — a worktree, your up command, and a public preview route (https://<branch>.<domain>, plus one host per service the stack declares) — and is then driven green against your check before anybody reviews it. The only difference is whether there is a feature to write.

1 · The thing you labelled

The states are the labels you can see on GitHub, so the status page and the issue (or PR) always agree. Exactly one agent:* label is set at a time.

2 · While it is agent:in-review

This is where a PR spends most of its life. Each loop is triggered once per cause — a comment id, a failing head commit, a base tip — so nothing can spin.

3 · One job

Every arrow in the two diagrams above is a row in the job queue: build, adopt, review, revise, discuss (a /pr-daemon comment on an issue with no PR: the agent replies on the issue and changes nothing), ci, merge, teardown, restart. Each has a unique trigger key (the label event id, the comment id, the failing head sha…), so one thing happening on GitHub starts exactly one job, ever.

4 · One preview stack

Two probes, because they answer different questions: the stack's own address says whether the app is running, and the public preview URL says whether a person can use it. Only the first is something a restart can fix. A restart is down then up, with PR_DAEMON_KEEP_DATA=1 set for down: the stack's data survives if the project honours it, and goes if it doesn't.

Who may start any of this

Everything an agent is given has to come from allowed_users: whoever added the label, whoever wrote and edited the issue's title and body — and, for a PR you label, whoever wrote and edited the PR's title and body, because that is the reviewer's input. A PR from a fork is refused: pr-daemon makes a worktree from the branch and pushes fixes back to it, which a fork's branch cannot do. Both refusals are said on the issue or PR itself.
